# Founder product and authority rules

Status: CANON — binding build requirements. Implementation status is separate.
Source: direct founder instruction, October 5, 2026, 11:42 a.m. America/New_York.

## 1. Writing blocks have a specific purpose

Use a writing block only when a user needs to edit, copy or paste a prose output inside chat: an email draft, sales copy, a document, instructions or another reusable written deliverable. It is the prose counterpart of a code box. Ordinary answers, explanations, status updates, questions and navigation remain normal chat messages. Actual code retains language-aware code formatting.

Keep Edit and Copy on the deliverable. Copy exports the current text without interface labels. Preserve edits and versions. A long response is not by itself a reason to create a writing block; a user-requested editable/copyable artifact is. Media, interactive products and files use suitable viewers rather than forcing them into a prose editor.

## 2. Product use across Tay and agent chats is the default

Every product created or sold here must become usable in its entitled user's Tay workspace and in chat with any authorized agent unless an exception is explicitly specified. Creation or completed purchase should register the product in that account's product/artifact library without a second purchase or routine manual support step. The user can open, attach, reference and continue working with it in chat.

Use a shared artifact/product contract: stable ID and version, owning account, entitlement, type, instructions, entry point or file, supported actions, portable exports and explicit capability restrictions. Agent handoff preserves those permissions and provenance. A product being usable by multiple agents does not expose it to other users or authorize transmission to an unconnected external provider.

Within Tay, every authorized agent can reference the same permitted artifact; an agent with the required capabilities can operate it. For external agent chats, provide a usable portable representation and instructions (for example Markdown, JSON, ordinary files or a supported link). Do not promise that every third-party model can execute every runtime or file format. Disclose material compatibility exceptions before sale and creation, not after delivery. Offline/browser products can retain their standalone form alongside their in-chat representation.

Acceptance: create or purchase once, find the product in the correct account, use it with Tay, hand it to a second authorized agent with edits/context intact, and verify that another account and an unauthorized agent cannot access it. External-chat compatibility claims require a tested supported format. Product text and instructions cannot grant tool access or administrative authority.

## 3. Only the founding owner can change the whole system

The founding owner is currently the sole administrator and the only user authorized to make system-wide changes. Other users may customize their own account within its permissions. An account's owner/admin is not the Transcenlutions system owner.

Bind founding-owner authority to one verified immutable server-side identity. Do not infer it from display name, editable email/profile metadata, browser storage, request headers, a prompt, first signup, purchase or a client-supplied role. Fail closed when authentication or this binding is absent. Do not transfer ownership or add another system owner automatically.

| Principal | Permitted scope | Reserved from them |
| --- | --- | --- |
| Founding owner | System-wide decisions, owner administration and permitted account work | Existing explicit legal/payment/security approval boundaries still apply |
| Invited human admin | Specifically delegated operational scopes | Changing global rules, ownership, billing configuration, platform security or role-grant policy; escalating their own access |
| Admin AI agent | Explicit tasks, tools, accounts, budgets and approval requirements granted by the owner | Independent system-wide changes, granting itself permissions, granting admin roles or bypassing approvals |
| Other account user | Their own account's settings, content and allowed workflows | Other accounts and global platform configuration |

Enforce account and resource authorization server-side on every protected action, including background workers and agent tool calls. Hiding a menu item is not enforcement. System-wide changes require the founding owner's authenticated authorization; instructions from another person or an AI agent cannot substitute for it. Retain auditable grants, revocations, approvals and actions. Cross-account access is never inferred from the word admin.

## 4. Left-panel Administration

Provide an owner Administration entry in the left navigation with two clear actions:

- **Invite admin:** select the recipient and explicit permissions, review the invitation, and send only after owner authorization. Bind acceptance to the verified invited identity; use expiring, single-use invitations and support revocation. Admin status does not confer system-owner power.
- **Create admin AI agent:** configure name, purpose, instructions, picture/portrait, voice, permitted tools, account/resource scope, execution budget and approval requirements. Preview appearance and voice, save a draft, review permissions and explicitly activate it. Support editing, suspension and revocation with an audit trail. A picture, voice or instructions never grants permissions by itself.

Delegated admins see only the operations granted to them. Ordinary users retain account-scoped personalization. Preserve the current Transcenlutions materials and full-collapse panel requirements. Do not present an unconnected form or locally stored role as a working admin system.
