# Approval-review calls: isolated source proposal

October 10, 2026. This proposal is separate from [native PR72](https://github.com/transcenlutions25/transcenlutions/pull/72) and today's reviewed integration candidate. It changes no native, UI, runtime, authentication, database or deployment files. It creates no push credentials, real calls, notification channels, microphone capture, telephony account or scheduled worker.

## Implemented planning kernel

`lib/approval-call-coordinator.ts` is a deterministic contact/approval-review coordinator, with synthetic tests in `scripts/check-approval-call-coordinator.mjs`. It consumes server-authoritative pending records and owner preferences; it emits descriptors only. No descriptor is dispatched by this module.

- Call-review invitations for each item or a batch threshold (including 3, 5 or a custom integer). Per-item and chat-only item overrides are supported. Thresholds count currently eligible, not-yet-offered item revisions, or explicitly due repeat/snooze revisions. Already announced unresolved items stay pending in chat; new arrivals do not silently cause repeated calls for the whole backlog.
- Minimum spacing, explicit repeat interval or no automatic repeats, local-calendar daily cap, IANA time zone, weekday/time windows, quiet hours crossing midnight, and snooze. Time windows are half-open; equal start/end is invalid rather than ambiguously all-day. Empty allowed windows means any time outside quiet hours. Server time must be monotonic; stale/future authority snapshots fail closed. UTC elapsed time governs spacing across DST transitions.
- Offline, denied notifications, unavailable voice, another active call, disabled policy, quiet hours, schedules and cadence retain pending work with an in-app/chat fallback descriptor. These descriptors do not themselves send chat messages. An unanswered ring is cancelled when it expires, connectivity/voice disappears, policy disables it, or quiet/scheduled availability closes. Quiet hours limit new/unanswered invitations, not an already accepted review.
- Generic notification text exposes no recipient, action, sensitive preview, amount or credentials on the lock screen. An invitation is account/session/device-bound, short-lived and idempotent in committed coordinator state. Answer opens authenticated review with microphone **off**. Decline dismisses the invitation, not its approval items. Snooze explicitly reschedules once without requiring automatic repeats. Interrupted and snoozed continuations retain their valid remainder even below the original batch threshold; they still obey quiet hours, cadence and daily caps. A deliberate decline or naturally missed call does not force a redial.
- Every item retains action ID, version, server payload digest, destination, scope, data summary, risk, consequences, exact cost/currency/commitment/terms and expiry. Any changed record invalidates that item’s invitation/review binding. An accepted review prunes changed, expired or resolved items and retains its unchanged remainder. The invitation/review deadline is independent of each item’s expiry; one short-lived item cannot strand the others. Expired/removed items cannot be approved from stale notifications.
- A specific item choice creates only an `uncommitted-approval-choice`, with a stable request ID and the exact normalized item/account/session/device binding. It grants no permission, removes no pending item, and executes nothing. Replays do not emit a second intent; a reused request ID cannot change its action/choice, and a new ID cannot replay the same reviewed revision. Hearing the list, answering, silence, a generic “yes,” or an `approve-all` event are never approvals. Handoff-only or unquoted-cost items cannot produce an affirmative choice here; they stay subject to the real approval/handoff flow.

The existing [governance rules](tay-engine-box-2-governance.md), [authority boundaries](agent-authority-boundaries.md), and founding-owner binding remain authoritative. The public `/api/agent/policy` endpoint is advisory and intentionally rejects client-minted approvals. Do not turn this module's choice into its `approved` boolean or call an execution helper with that boolean.

## Trust and persistence required before connecting it

Use `evaluateApprovalCalls` with a real `ApprovalAuthority.resolve` adapter on **every** operation, including empty polls, duplicate decisions, answer and snooze. Resolve the immutable owner/account mapping, authenticated session, active device, current membership, current pending records and saved owner preferences on the server. A client role, supplied `ownerVerified` boolean or cached snapshot is not authority. The exported pure transition is a test/planning kernel, not a public authorization boundary. The adapter supplies a trusted server clock callback, sampled after asynchronous authority resolution, and must check fresh time/authority again before dispatch and approval commitment.

Coordinator state is trusted server-owned state, never a request-body or browser-storage grant. Persist its next state and invitation/decision outbox atomically with compare-and-swap against the independent `stateVersion` before dispatch. `revision` tracks authoritative pending/preferences snapshots and is not a storage CAS token. One server lease chooses the recipient device and prevents phone/tablet/computer double ringing or double acceptance. A reconnect may re-deliver an already committed invitation ID; the native adapter must suppress duplicate display. Invitation IDs are only unique inside their persisted coordinator; dispatch keys must include tenant/user/session/device scoping. Do not generate a new ID to retry an uncertain dispatch/decision. If authority fails or account/session changes, clear/cancel visible protected review and notifications; never expose the previous account's preview or auto-answer.

Rejected events can carry a non-enumerable, server-internal `ApprovalCallError.reconciliation`: next state and cancellation/review-update effects computed before handling the rejected event. The adapter must CAS-commit this cleanup separately from the rejected choice, or re-resolve and reconcile again after a conflict. It contains no new intent or invitation from that rejected event. Never serialize the error’s internal state, dedup history or previews in a public error response. Authentication/scope/stale-snapshot/clock failures before reconciliation carry no protected state; the delivery/UI adapter must cancel or hide the protected view and refresh through current authority. Chat fallback is an idempotent status descriptor, not a repeated chat-send instruction.

The actual approval service must revalidate authority, item version/digest, expiry, immutable preview, applicable policy and required action-time confirmation/handoff. It must commit an audit record and a single-use bounded execution authorization in one transaction. Executing a task/payment/tool action is a separate worker action with its own idempotency and current authorization. No offline decision is executable; disconnected observations/choices remain unconfirmed until server validation and, when stale, renewed per-item review. This proposal stores neither raw audio nor a voice biometric.

The reference kernel accepts at most 1,000 snapshot items and 4,096 history entries per category, failing explicitly at capacity instead of silently deleting dedup evidence. These are defensive source-proposal bounds, not a product backlog promise. A production adapter needs durable pagination and an audited retention/compaction policy. There is no persistence/restore codec, database migration, push outbox, server lock, sign-in provider or approval endpoint in this slice.

## Smallest Android implementation path

1. Reuse the existing Tay account, conversation and approval backend once it actually exists. Save opt-in contact preferences there; default off until the owner deliberately configures them. Use a selected device and opaque short-lived invitation reference; fetch sensitive previews only after current authentication.
2. Implement an ordinary actionable Android notification for “Review approvals,” with open/decline/snooze actions using explicit immutable PendingIntents. Request `POST_NOTIFICATIONS` in context on Android 13+. User/channel sound settings and Do Not Disturb control whether it audibly alerts. Denial falls back to the pending chat/review list; no repeated permission prompts or policy-access bypass.
3. After the owner accepts, open the visible Tay Activity, revalidate the invitation/account, show the exact per-item review card and allow an in-app voice session only through the clear owner action and applicable microphone consent. The invitation must never auto-answer or open the microphone. Each affirmative decision names one action and its exact preview/cost/scope; do not infer blanket acceptance from a transcript or reading out a batch. Ambiguity stays pending, with explicit per-item chat controls.
4. The first implementation can keep audio foreground-only, reusing PR72's capture cancellation on pause. If ongoing background audio later becomes necessary, add a separately reviewed microphone foreground service and its visible ongoing notification, service type and required permissions; start it through a permitted user-visible path. Do not start microphone capture merely because a push message arrived.
5. Only if Tay implements genuine in-app VoIP/call semantics should `CallStyle`/Telecom integration be evaluated. Self-managed-call notification exemptions require the complete Android setup, not one manifest permission. A pending-approval reminder is not automatically eligible for full-screen incoming-call privileges. Do not request full-screen intent, default-dialer role, `MANAGE_OWN_CALLS`, phone/SMS access, Accessibility, exact-alarm access or battery/DND exemptions for this proposal.

Cloud push setup requires a real authenticated backend/device-token mapping and separate credentials/security approval. Delivery can be delayed or unavailable while offline, under power restrictions, or when notifications are disabled. Standard periodic WorkManager intervals are at least 15 minutes and timing is inexact; it cannot satisfy an arbitrary exact ring schedule. Evaluate server reminders plus supported push later, with honest delivery status and chat fallback. High-priority FCM is for genuinely time-sensitive user-visible content, not an unlimited background execution/microphone entitlement. No provider, account, free tier, push grant, phone number or fee-free voice/model service is assumed here.

## Required acceptance before activation

- Real owner sign-in and per-request revocation; wrong tenant/user/device/session, stale notification, duplicate push, simultaneous phone/tablet answers, server CAS conflicts and restart recovery; rejected-event cleanup, completion/expiry of one item during batch review, partially expired snoozes, nested per-item snoozes, interrupted-call recovery, and authority/time changes while resolution is pending.
- Notification denied/revoked, channel muted, DND, device locked, offline/Doze, missed ring, quiet-hour boundary, timezone/DST changes, snooze beyond expiry, scheduled time missed, batch thresholds 3/5/custom and per-item mode. Show unsent/undelivered/expired states honestly.
- Answer never opens audio before the owner-visible consent path. Background/lock/app switch and another call stop or safely suspend capture. No auto-answer, repeated microphone restart, secret recording or raw-audio retention.
- Preview/risk/recipient/scope/cost/terms change during spoken review; transcript ambiguity, “yes” without a named active item, “approve everything,” cancelled/expired action, handoff-required item, network failure after choice and duplicate receipt. Only the server's exact, fresh, single-use decision can authorize the separately governed action.
- Test on real Android 12/API31 and current Android devices, including TalkBack, large text, keyboard, headset/audio focus and OEM restrictions. This pure TypeScript test suite establishes none of that native behavior.
